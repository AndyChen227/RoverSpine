# 2026-09-13 — ERC Is 44, Not 30 / ERC 是 44，不是 30

## Result / 本次结果

**The ERC number committed in
[the entry a few hours ago](2026-09-13-erc-severities-tightened.md) is wrong.**
Against the files as committed, ERC reports **44 errors / 0 warnings**:

几小时前那篇里写下并提交的 ERC 数字是错的。对着**已提交的那份文件**跑，ERC 是
**44 错误 / 0 警告**：

| Rule | Count | Status |
|---|---|---|
| `pin_not_connected` | 30 | By design — the unused pins on the 2×20 Pi header |
| `footprint_filter` | **14** | **One per symbol — J1, J2, R1–R12** |

Nothing is wrong with the board. **The schematic, the nets, the values and the
netlist check are all untouched and still correct** — `check_nets.py` still
reports `ALL PASS`. What was wrong is a number in two documents, and the
reasoning that produced it.

板子没有问题。**原理图、网络、阻值、网表核对全都没动，也依然是对的**——`check_nets.py`
仍然 `ALL PASS`。错的是两份文档里的一个数字，以及得出那个数字的推理。

---

## What the rule actually does / 这条规则实际上在做什么

The previous entry claimed:

> `footprint_filter` compares an **assigned** footprint against the filter
> patterns declared on the symbol. Rev A has **no footprints assigned**, so today
> the test has nothing to compare and cannot pass or fail.

**That is false.** The report says so in the clearest possible way:

上一篇写的是"Rev A 一个封装都没分配，所以这项检查没有比对对象，既通不过也不会失败"。
**这是假的。** 报告用最直白的方式说明了这一点：

```
[footprint_filter]: 已分配封装 () 与封装筛选规则 (Connector*:*_2x??_*) 不匹配
    ; error
    @(39.37 mm, 58.42 mm): Symbol J1 [Conn_02x20_Odd_Even]
```

Look at the `()`. **The empty footprint field is compared like any other value,
and empty matches nothing.** "No footprint assigned" is not zero violations — it
is fourteen, one for every symbol that declares a filter.

注意那个 `()`。**空的封装字段和任何别的值一样参与比对，而空不匹配任何规则。**
"没有分配封装"不是零条违规，**是十四条**——每一个声明了筛选规则的符号一条。

## The experiment / 判决性实验

The disagreement was worth settling properly rather than by insisting, because
there was a live possibility that `kicad-cli` simply ignores the project file's
severities and uses its own defaults — in which case the `44` would have been the
artifact and the `30` correct.

Three copies of the same schematic, in a scratch directory, differing **only** in
one severity in the project file:

这个分歧值得用实验而不是用坚持来解决，因为有一种很实在的可能：`kicad-cli` 根本不读工程文件里的
严重性，而是用它自己的默认值——那样的话 44 才是假的，30 才是对的。

同一张图复制三份，**只改工程文件里的一项严重性**：

| Variant | `footprint_filter` | `pin_not_connected` | Violations |
|---|---|---|---|
| **A** — as committed | `error` | `error` | **44** = 30 + 14 |
| **B** | `ignore` | `error` | **30** |
| **C** | `error` | `ignore` | **14** |

**C proves `kicad-cli` reads the project's severities** — turning off a rule
removed exactly its own violations. **B is the important one: it returns exactly
30.**

C 证明 `kicad-cli` 读得进工程里的设置——关掉一条规则，正好少掉那条规则的违规。
**B 才是关键的那个：它正好回到 30。**

So the `30 / 0` was not a mistake in reading, and not a different board. It is the
**correct** report — for `footprint_filter: ignore`. The run happened in the world
before the setting changed; the file on disk is the world after. The number and
the file were one step out of sync.

所以那个 `30 / 0` 不是看错，也不是另一块板。它是**正确的**报告——`footprint_filter` 还等于
`ignore` 时的正确报告。**那次运行发生在设置生效之前，磁盘上的文件是生效之后。数字和文件差了
一步。**

## Two confirmations that were not independent / 两个并不独立的确认

This is the part worth keeping.

The number `30` arrived twice, from what looked like two directions:

1. **By reasoning** — "the check cannot fire, because there is nothing to
   compare", written into a devlog.
2. **By observation** — the ERC panel, reporting 30 / 0.

They agreed, so neither was used to check the other, and the entry was committed
and pushed.

But the panel's `30` came from a run made **while `footprint_filter` was still
`ignore`** — which is precisely the world the reasoning described. The prediction
said "this rule contributes nothing"; the measurement was taken from a run in
which that rule contributed nothing **because it was switched off.**

`30` 这个数字是从看起来两个方向来的：一个是**推理**（"它开不了火，因为没有比对对象"），一个是
**观察**（ERC 面板报 30/0）。两者一致，于是谁也没拿来检查谁，那篇就提交并推上去了。

但面板上的 `30` 来自**一次 `footprint_filter` 还是 `ignore` 时的运行**——恰恰就是那段推理描述的
世界。推理说"这条规则不贡献任何东西"，而测量取自一次"这条规则确实没贡献任何东西——因为它被关着"
的运行。

> **A prediction and a measurement that agree are worth something only if they
> could have disagreed.** These two could not. They were the same mistake wearing
> two hats, and the agreement between them felt like corroboration while being
> nothing but an echo.
>
> **一个预测和一次测量相互印证，只有在它们本来可能不一致的时候才有价值。** 这两个不可能不一致。
> 它们是同一个错误戴了两顶帽子，而它们之间的一致看起来像互相佐证，实际上只是回声。

This is the same failure shape [this morning's
entry](2026-09-13-twelve-resistors-drawn.md) recorded about ERC and the swapped
label — **a report that looks identical with and without the fault** — arriving
from the other side. There, the tool was silent about a real fault. Here, the
tool was accurate about a state the file was no longer in.

## Where the number came from: a panel, not a run / 那个数字的来源：一块面板，不是一次运行

[The netlist check was made reproducible on
09-12](../../hardware/stage1-signal-adapter/tools/README.md) for exactly this
reason: a result pasted from a GUI is a claim about a moment nobody can re-enter.
**ERC was left as the one check that still lived in a panel** — and that is the
check that went stale.

KiCad's ERC panel does not re-run when a severity changes. It keeps showing the
last run, which is correct behaviour and completely indistinguishable, on screen,
from a fresh one.

09-12 之所以把网表核对做成可复现的，理由就是这个：**从 GUI 里复制出来的结果，是一句关于某个
谁也回不去的时刻的断言。** 而 **ERC 是唯一还住在面板里的那项检查**——过期的正是它。
KiCad 的 ERC 面板不会因为你改了严重性就自己重跑；它继续显示上一次的结果，这是正确行为，
而且在屏幕上和一次新的运行**长得完全一样**。

So ERC now leaves the panel too. The command is committed in
[`tools/README.md`](../../hardware/stage1-signal-adapter/tools/README.md):

于是 ERC 也搬出面板。命令已经提交在 `tools/README.md` 里：

```bash
kicad-cli sch erc --severity-error --exit-code-violations \
  -o erc.rpt RoverSpine_Signal_Adapter_RevA.kicad_sch
```

`kicad-cli` is **KiCad 10.0.6**, already installed at
`%LOCALAPPDATA%\Programs\KiCad\10.0\bin\`. It was there the whole time; the
earlier session looked in `Program Files` and on `PATH`, found neither, and
concluded ERC could not be run from a script. **That wrong conclusion is what
left the check in the panel for one more day.**

`kicad-cli` 就是 **KiCad 10.0.6**，本来就装着。之前那次只查了 `Program Files` 和 `PATH`，
两处都没有，就断定 ERC 没法脚本化。**正是那个错误结论，让这项检查在面板里多待了一天。**

## The decision stands, on a better reason / 决定不变，理由更好了

`footprint_filter: error` is kept. The previous entry defended it as a rule that
costs nothing because it cannot fire. It can fire, it is firing, and that is
**better** than the defence offered for it:

**Those 14 errors are the footprint-assignment to-do list, and the list empties
itself.** The count goes to zero at precisely the moment all fourteen footprints
are assigned *and match their symbols' filters* — not when they are merely
assigned. A wrong-pitch or wrong-pin-count footprint keeps its error on the
board.

`footprint_filter: error` 保留。上一篇替它辩护的理由是"它开不了火，所以不花钱"。它开得了火，
它正在开火，**而这比那条辩护好**：

**那 14 条错误就是封装分配的待办清单，而这张清单会自己清空。** 计数归零的时刻，正是十四个封装
全部分配**并且匹配各自符号的筛选规则**的时刻——不是"分配了"就行。配错间距或错引脚数的封装，
它那一条错误会留在板上。

这一个可以放心押下——因为和上一个不同，它会被一条**对着文件运行的命令**检查，而不是被一块面板。
